# Stocktake, 2026-11-17

*Written at the November revisit, before the unit pilot. Triggers: the M5 Ultra
(256 to 512 GB unified) on the way, Kindi's appearance, the recurring "Ollama is
leaving llama.cpp speed on the table" question, and the honest feeling that the
service list has become trial-and-error sediment. Reads
[the handover](handover-2026-10.md) and resolves its open decisions where
evidence now exists.*

## The verdict

**The architecture holds. No rebuild.** The three-way split (Tier 1 ours:
assessment, orchestration, policy / Tier 2 capability pipelines / Tier 3
catalog) survived every new fact this month, including two that looked like
threats. What is wrong is narrower and fixable: decisions recorded in October
were never executed, and the shipped defaults still do not match the vision
document. This stocktake executes them and records the two genuinely new
decisions (ADR0013, ADR0014).

## Decision A: the engine — resolved as one default per deployment class

[ADR0012](adr/0012-localai-as-engine-and-the-catalog.md) named LocalAI *the*
engine. It has never been started. The honest resolution is that "the engine
slot" was always an over-generalisation: the deployment classes have different
winners, and pretending otherwise is what kept the migration stuck. Resolved as
[ADR0013](adr/0013-engine-per-deployment-class.md); ADR0012 is amended, not
superseded, because its catalog half stands unchanged.

| Deployment class | Default engine | Why |
| --- | --- | --- |
| NVIDIA + concurrency (unit pilot, ~40 students) | LocalAI with the vLLM backend | the only real concurrent-serving answer; Decision L's trigger fired |
| NVIDIA single small card (8 to 12 GB) | llama.cpp server, flags generated by `puente init` | ADR0010 promoted from alternative to default: the operator controls the flags Ollama does not expose |
| Easy path, including Apple Silicon (the M5) | Ollama | its actual product is operational ease, and it is genuinely fine there |
| The floor (old or tiny cards, DDR3/4 boxes) | undecided — benchmark Kindi vs llama.cpp `-ncmoe` | see below |

## Kindi: evaluated 2026-11-17, verdict: benchmark at the floor, do not adopt yet

Recorded like the QVAC entry so it is not re-litigated. Sources:
`amirhusain.com/software/kindi/` (v0.6.1), `github.com/ahtx/kindi`.

What it is: a local inference engine, AGPL-3.0, Docker on Linux/Windows,
OpenAI-compatible API on :8093, built for **low-cost and old GPUs** (Kepler
through Blackwell, plus Radeon iGPUs and x86 CPUs). Expert-offload to host RAM
plus built-in speculative drafters (DSpark/DSpine). The measured wins against
llama.cpp on the same card and model file are large exactly where this project
lives: 30B-A3B at 89.5 tok/s on a GTX 1080 (llama.cpp: 4.7); 552B MoE at
18.7 tok/s on a 3060 + DDR4 server. On modern RTX cards the win is modest
(1.0 to 1.5x).

Why not adopted now:

- **It runs a curated model list** (Bonsai ternary, Nemotron Lightning,
  Nanbeige, DeepSeek Flash), not arbitrary GGUF. It cannot replace
  llama.cpp/Ollama; it competes for the ADR0010 floor niche only.
- v0.6.1, single maintainer, benchmarks self-reported (though methodologically
  careful: same card, same file, same context).
- AGPL-3.0: fine for education use, must be surfaced like YuE2's NC licence at
  install time (Decision F's licence-field pattern).
- **Encroachment warning shot, third of its kind** (QVAC's registry,
  Odysseus's Cookbook, now Kindi's installer): it finds the cards and recommends
  a setup, which is `capabilities.py`'s job. Watch it.

Revisit trigger: the floor-hardware benchmark. Kill condition: if it does not
beat llama.cpp `-ncmoe` by at least 2x on models we actually ship, it becomes a
catalog note and nothing more.

## The llama.cpp speed question: resolved by ADR0013, verified by one benchmark

Ollama wraps llama.cpp but pins and backports, so kernel wins arrive late and
flags such as `-ncmoe` are not all exposed. That was true before this month and
the answer is not "leave Ollama": it is the per-class default above. One action
before the pilot: an afternoon benchmark on the 4060 Ti — Ollama vs
llama.cpp-server-direct, same model, same quant, and the flag set `puente init`
would generate. Whichever wins becomes the small-card default in fact, not just
in an ADR.

## Decision B: resolved — both stay, jobs split

New fact from the operator: **AnythingLLM's embed is the feature.** Workspace,
upload documents, export as an embedded chatbot, get a floating "+" on any
page. It is in production for the webpage chatbot and nothing else in the stack
does white-label embedded chatbots. Decision B therefore does not resolve to
"one goes"; it resolves to a jobs split:

| Surface | Its job |
| --- | --- |
| **AnythingLLM** | embedded chatbots (unique, in production) |
| **Open WebUI** | the default harness, chat view |
| **LibreChat** | catalog-tier; retained for the pilot because the side-by-side local-vs-frontier comparison is a teaching feature (Decision I) |

One premise corrected along the way: **Open WebUI has auth.** Multi-user
accounts plus OIDC against the institution IdP, exactly as Decision I recorded.
Auth was never the blocker.

## Decision C: the opinionated default, finally opinionated

Eight services for a fresh install, as `services-inventory.md` already
sketched: engine (per class), Open WebUI, SearXNG, ComfyUI + SwarmUI, Voicebox,
Speaches, ACE-Step, Caddy, portal. Executed now:

- **Chatterbox**: deleted (already retired; Voicebox subsumes it).
- **Fooocus, MusicGen**: catalog entries marked legacy. Off, discoverable, no
  service class.
- **SwarmUI stays** the opinionated image door (it is the working
  `image.locopuente.org` today and the wait-gate work hardened it); ComfyUI
  remains the node host beneath it.
- The decision layer routes the five capabilities, not eight; the research and
  tools groups stay reachable by name.

## The M5 Ultra: what changes, what does not

Changes: **residency policy dissolves** on 256 to 512 GB unified. Every model
fits resident; load-and-release stops being the design on that box. The engine
is llama.cpp Metal (or MLX); vLLM does not apply on macOS.

Does not change: the institutional layer is the differentiator there — OIDC,
fair-share queueing, snapshots, per-semester pinned models, the catalog. The
pilot's feature list *is* the M5's prerequisite list. The hardware swap is the
easy part, as the project brief predicted; the new box is a deployment shape,
not a new architecture.

## The harness as operating system (extends Decision H)

The operator's named end-state: **one browser surface, mode-selectable** (chat,
deep research, literature review, podcast, quiz, deck, data analysis),
frontier-equivalent *functionality* on local models while accepting
not-frontier performance, and the less each capability feels like a separate
app, the lower the friction. This is Decision H's 80/20 harness with the
product surface finally specified.

The honest framing, unchanged from October: **this is the harness's job, and
Puente refused to write a fourth chat interface.** The path to it is wiring,
not building — and most of the wiring is config, not code:

| Capability | Today | Path into the one harness | New code |
| --- | --- | --- | --- |
| Chat | Open WebUI native | none | none |
| Image | SwarmUI API door | already wired (Decision H) | none |
| Voice STT/TTS | Speaches/Voicebox APIs | Open WebUI accepts OpenAI-compatible voice endpoints | config |
| Search | SearXNG | already wired 2026-10-17 | none |
| Slides | Presenton ships `/mcp` | MCP tool (Decision H's ~30 min item) | config |
| Data analysis | code interpreter built-in | enable it; test with `gemma4:12b` (K3) | config |
| Deep research | Vane, own UI | harness card or tool; link-out at first | small |
| Podcast/quiz | Open Notebook (catalog) | second door at first; API tool later | none |
| Docs/decks/sheets as files | none | tool-calling: a qwen3-class model drives a file-output tool (.docx/.pptx/.xlsx), the local "Claude Office" equivalent | one MCP tool |
| Video (S2V, avatars) | ComfyUI nodes | power view only, not a harness mode | none |
| Embedded chatbots | AnythingLLM | stays AnythingLLM; not a harness job | none |

Build-only-if rule, restated: wire upstream first; write code only where no
upstream harness can drive the stack's APIs. If Open WebUI + MCP cannot carry
the office surface after a real attempt, *that* is the moment to reopen
"our own harness", not before.

## The tiers (ADR0014)

The deployment story is three tiers, recorded in
[ADR0014](adr/0014-deployment-tiers-native-quick-start.md):

| Tier | Shape | For whom |
| --- | --- | --- |
| **1. Suitcase** | native, no Docker: engine + Open WebUI (pip) + Caddy binary | one operator, one classroom, modest hardware; the mochila-shaped rung |
| **2. Stack** | today's compose stack, all capabilities | the PoC, the pilot, an institution's first server |
| **3. Campus** | tier 2 + OIDC forward-auth + fair-share + snapshots + upgrade path | the product end-state; what the M5 deployment runs |

Tier 1 exists because "Docker is a means, not the goal" (handover design
principle): `nvidia-container-toolkit` is the hardest prerequisite
`puente doctor` checks, and the easiest possible setup for a non-expert should
not require it. Tier 3 is configuration and wiring of an upstream harness, not
a new UI.

## The benchmark protocol

Three benchmark pairs are queued: llama.cpp-direct vs Ollama on the 4060 Ti;
Kindi vs llama.cpp on the spare floor box; and Ollama vs an `mlx-lm` server for
the M5 class. All three answer one question with one metric: **seconds to an
acceptable answer** — quality-weighted time.

- **Quality is measured, not vibes.** A fixed set of pilot tasks (quiz from a
  text, feedback on a paragraph, one small data-analysis question), identical
  prompts per engine, scored against a rubric. The unit already owns a rubric
  approach (VET); reuse it rather than inventing an eval harness.
- **Speed is tok/s at a realistic context**, not a peak short-context number.
- **The composite is the metric.** A 30 tok/s model that needs three
  corrections loses to a 6 tok/s model that lands it first: rework dominates
  past a threshold. "Even high quality is not worth the wait" is the same curve
  read from the other side.
- **The Kindi wrinkle.** Its drafters (DSpark/DSpine) claim output-identical
  decoding, so the *engine's* speed gain does not trade quality. The quality
  risk sits in the *models* it runs: ternary and low-bit weights (Bonsai,
  Nemotron Lightning) are exactly where quality drop is likeliest. So the
  Kindi test scores task quality of those models against a standard Q4 GGUF of
  similar size, not just tok/s.
- **The Apple-path fact, recorded so it is not misremembered:** Ollama does not
  install MLX underneath; on macOS it is llama.cpp with Metal. Choosing MLX
  for the M5 means adding an `mlx-lm` server (OpenAI-compatible) as an engine
  option — hence it enters the benchmark as a candidate for the Apple class,
  not a default (ADR0013).
